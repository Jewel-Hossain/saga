    Terms used here

    Dual write
    Writing to the database and publishing to the broker as two separate steps. There is no transaction spanning both, so a crash between them leaves one done and the other not.
    Transactional outbox
    Insert the event into an outbox table in the same local transaction as the business change. The event becomes durable exactly when the order does.
    Message relay (polling publisher)
    A separate process that reads unsent outbox rows, publishes them, and marks them sent once the broker confirms.
    FOR UPDATE SKIP LOCKED
    Lets several relay instances poll the same table without picking up the same row twice at the same moment.
    Publisher confirms
    The broker sends basic.ack to the publisher once the message is persisted in every routed queue. The relay only marks a row sent after that ack.
    At-least-once
    What the outbox guarantees. If the relay dies between the confirm and the UPDATE, it publishes the same row again after a restart.
    Idempotent consumer (inbox table)
    The consumer records each message_id in processed_messages in the same transaction as its side effect, so a duplicate becomes a no-op.
    Log tailing (CDC)
    An alternative relay: a tool like Debezium reads the database's write-ahead log instead of polling, giving lower latency and no extra query load. The guarantees are the same.
    Ghost event
    A message describing a change that later rolled back. Once published it can't be recalled, and consumers act on something that never happened.
