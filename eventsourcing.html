Event sourcing

The order isn't stored as a row. It's stored as the list of things that happened to it, and the current state is whatever you get by replaying that list. Commands are checked against the replayed state, accepted ones become new events, and read models are built by projecting the same events.

    Terms used here

    Event store · stream
    An append-only log of events per aggregate (here order-1042). Events are never updated or deleted; corrections are new events.
    Aggregate · rehydration
    The object that enforces the business rules. To handle a command it replays its stream from the start (or from a snapshot) to rebuild its current state.
    Optimistic concurrency
    Every append says which version it expects the stream to be at. If someone else appended first, the store rejects it with WrongExpectedVersion and the handler reloads and tries again.
    Snapshot
    A cached copy of the aggregate state at some version. Loading becomes "snapshot + events after it" instead of the full stream. It's an optimisation and can always be thrown away.
    Projection · read model
    A query-friendly table built by applying events in order. It is eventually consistent and owns a checkpoint saying how far it has read.
    Replay
    Reset a projection's checkpoint to 0 and apply every event again. That's how bugs in read models are fixed and how new read models are built from old history.
    CQRS
    Separating the write model (aggregate + events) from the read models (projections). Event sourcing almost always comes with it.
