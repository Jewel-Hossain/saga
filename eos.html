Kafka exactly-once

A stream processor reads payments, writes ledger entries and commits its input offset. With plain consumers those are three separate writes, so a crash in between duplicates output. Kafka transactions make the output records and the offset commit one atomic unit, and fence off zombie instances.

Producer, consumer and transaction coordinator requests

    Terms used here

    transactional.id
    A stable id per processor (per input partition). It lets the coordinator recognise a restarted or duplicate instance as "the same producer".
    initTransactions · epoch
    On startup the producer registers its transactional.id. The coordinator aborts any open transaction for it and bumps the epoch; older epochs are fenced.
    sendOffsetsToTransaction
    Writes the consumer offset commit into the same transaction as the output records, so "processed" and "output written" become one atomic step.
    Commit / abort markers
    Control records the coordinator appends to every partition in the transaction. They decide whether the records before them count.
    read_committed
    Consumers only read up to the last stable offset and skip aborted records. read_uncommitted sees everything, including data from aborted transactions.
    Zombie fencing
    A paused instance that wakes after being replaced gets ProducerFencedException because its epoch is old, so it can't write duplicate output.
    Scope
    Exactly-once covers Kafka-to-Kafka processing. Side effects outside Kafka (emails, HTTP calls) still need idempotency.
