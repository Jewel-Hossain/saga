Retries, delays and TTL

What a RabbitMQ consumer should do when processing fails. Retrying in place blocks the queue, so failed messages are parked in delay queues whose TTL dead-letters them back when it's time to try again. Messages that can never succeed, or have expired, go to a parking-lot queue.

Retry topology

Delay queues have no consumers. Each one is declared with x-message-ttl and x-dead-letter-exchange=orders, so a message sits there for its delay and then flows back into orders.q. Time in delay queues is compressed.

AMQP methods and consumer decisions

    Terms used here

    Delay queue (TTL + DLX)
    A queue with no consumers, x-message-ttl and a dead-letter exchange. Messages wait out the TTL, then RabbitMQ republishes them to the DLX. That's how a delay is built from standard features.
    Retry tiers · backoff
    Several delay queues (5 s, 30 s, 2 min). The consumer picks the next tier from an x-retry-count header, so each retry waits longer.
    Parking lot (DLQ)
    Where messages go when retrying is pointless: retries exhausted, payload invalid, or expired. Nothing consumes it automatically; people inspect and replay.
    requeue=true
    Puts the message straight back at the head of the queue. With a persistent failure it's redelivered immediately, forever, burning CPU and blocking everything behind it.
    Retryable vs non-retryable
    Timeouts and 503s may succeed later. Validation errors and 4xx won't, so they should go to the parking lot on the first attempt.
    Message TTL · expiration
    The expiration property (or a queue-wide x-message-ttl) drops or dead-letters messages that waited too long. Good for data that goes stale, like price updates.
    x-death
    A header RabbitMQ adds on every dead-lettering, with the reason (rejected, expired, maxlen), the queue and a count.
